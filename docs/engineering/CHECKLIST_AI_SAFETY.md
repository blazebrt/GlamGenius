# AI safety review checklist

Use this checklist when the PR touches prompts, model routing, safety
rules, ingredient rules, appearance analysis, or any surface that
renders an AI-produced string to the user.

The product does not diagnose, prescribe, or dose. It does not score a
user's appearance. It labels itself when it is guessing. This checklist
is the mechanical part of holding that line.

## 1. Prompts

- [ ] Any change to a prompt bumps the corresponding
      `PROMPT_VERSION_*` constant so downstream logs know which prompt
      produced which output.
- [ ] Prompt strings do not embed unredacted user data. Personal
      identifiers are passed by reference (id, hash) or through the
      redaction wrapper.
- [ ] Prompt strings do not embed system-secret material (API keys,
      database URLs).
- [ ] The full prompt fits in the model's context window even for the
      largest realistic user payload.

## 2. Schemas

- [ ] Any change to the expected AI output structure bumps the schema
      version constant.
- [ ] The parser rejects extra keys the app does not expect, rather
      than silently propagating them into the database.
- [ ] The parser rejects missing required keys with a distinct error
      code (not "provider timeout").
- [ ] The parser rejects an unparseable response as an invalid-JSON
      failure, distinct from a quota failure and distinct from a
      timeout failure. Downstream metrics keep these outcomes apart.

## 3. Safety filter

- [ ] Every new AI-produced string that will be rendered to the user
      still passes through `safety.narrative_is_safe`.
- [ ] The filter is applied before the string is persisted, not only
      before it is displayed.
- [ ] The banned-word list is not bypassed by concatenation with a
      static prefix.
- [ ] A structured safety category exists (or an issue is opened) for
      any new pattern the reviewer catches by hand. Banned-word lists
      are a secondary defence, not the primary one. Work Package 3
      adds the primary layer.

## 4. Never-allowed patterns

- [ ] The AI-produced string does not contain a diagnosis.
      "You may have rosacea" is a diagnosis. "Redness is often
      associated with rosacea; a dermatologist can confirm" is not.
- [ ] The AI-produced string does not recommend a treatment intensity
      or dosage.
- [ ] The AI-produced string does not name a prescription medication.
- [ ] The AI-produced string does not compute or display an overall
      appearance score.
- [ ] The AI-produced string does not use the phrase "money wasted".
- [ ] The AI-produced string does not claim objective physical
      progress from photos ("your skin has improved 32 %"). Progress
      language is user-confirmed or labelled experimental.
- [ ] For supplements: inventory only, no dosage, no health claim, no
      interaction reasoning.

## 5. Failure handling

- [ ] AI failure does not consume the user's allowance (an unsuccessful
      call is not billed to the user's daily/monthly cap).
- [ ] AI failure does not persist a fabricated observation. On failure
      the record is either absent or explicitly marked as failed.
- [ ] Provider fallback (if the PR touches it) reports which provider
      answered.
- [ ] The retry policy is bounded and does not amplify a stuck request.

## 6. Ingredient rules

- [ ] Every deterministic ingredient warning added by the PR carries:
      stable rule id, version, severity, evidence source citation,
      reviewer name, reviewed date, applicability limits, exceptions,
      active/deprecated/disputed status.
- [ ] The evidence for the rule is a citation to a source a human
      wrote (peer-reviewed paper, monograph, regulator publication),
      not an LLM completion.
- [ ] Unsupported ingredients are labelled **not covered**, never
      **safe**.

## 7. AI-generated evidence

If part of the PR — text, tests, migrations, docs — was generated by
an AI coding assistant, the reviewer specifically looks for:

- [ ] Fake references (URLs that 404, papers that do not exist, quoted
      lines that are not in the cited file).
- [ ] Confidently wrong test assertions (a test that "passes" against
      the assistant's imagined output but not the real output).
- [ ] Reasonable-looking migration SQL that fails on the real schema.
- [ ] Confident narrative in the PR description that the diff does
      not support.
- [ ] Missing edge cases the assistant is known to miss: timezones,
      currency, unicode, empty collections, error paths.

The independent reviewer must be human (see
[`REVIEW_POLICY.md §3`](REVIEW_POLICY.md#3-what-counts-as-an-independent-reviewer)).

## 8. Evidence

- [ ] Provider-independent tests (`pytest -q tests`) are green.
- [ ] For a rule change, the corresponding safety test in
      `test_routines.py` (or successor) is added or updated.
- [ ] For a prompt change, the version bump is visible in the diff.

## 9. Sign-off

- [ ] Independent reviewer per [`REVIEW_POLICY.md`](REVIEW_POLICY.md).
- [ ] Owner approval per CODEOWNERS (`safety.py`, `rules.py`,
      `ontology.py`, `ai.py`, `ai_gateway/**`).
